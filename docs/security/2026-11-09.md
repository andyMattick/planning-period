well"). Scope: the static site (`site/`), the Vercel config and function (`vercel.json`, `api/`), Supabase

`scripts/run-order.mjs`, `scripts/orders.mjs`, `scripts/auditor-gate.mjs`, `scripts/notify-order.mjs`), dependencies,

How it was tested: by reading the code and migrations, and by running the repository's own tests against the fake

called** (in this session every call to it would carry the owner's service key, so it would prove nothing and could
change data). The public site was read with plain GETs only. Nothing was deployed, merged or changed in Vercel,
Supabase or GitHub settings.

Branch: `dominyk-security-2026-11-09`. Every fix has a check that would have caught it: `scripts/security-check.mjs`
(now `npm run check`, section 16, with a self-test that breaks each fixed file and expects the check to fail) or a new
case in `scripts/test-run-order.mjs` / `scripts/test-orders.mjs`.

## Critical

### 1. Agent sessions could reach the runner's secrets

**What.** The runner's agent sessions read the teacher's uploads, which are untrusted, and they may run `node` and
`python3`. They ran as the same OS user as the runner, with the runner's full environment (only the push token was
removed, and that removal didn't hold, because a same-user process can read its parents' environment). The GitHub
runner user also has passwordless sudo and docker.

**How it could be exploited.** A teacher (or anyone who gets a document into an order) hides instructions in an
uploaded source. If an agent follows them, it can read the Supabase service key (every teacher's orders, uploads,
previews and finals, read and write) and, in the final stage, the auditor's push token (write to `main`). Details are
in the fix commit and are not repeated here.

**Fix.** Commit `20638b4`: every agent session gets only non-secret variables (`sessionEnv`), and in the runner it runs
as a separate user, `ppagent` (no sudo, no docker, can't read the runner's processes; `run-order.yml` checks all three
before any order runs and stops if one fails). Session folders are lent to that user and taken back after each
session, with any links it made removed. `scripts/test-run-order.mjs` fails if any session sees a key, token or
password, and checks the sudo wiring with a stand-in sudo.

**Not tested here:** the real GitHub runner (useradd, sudo, the shared node_modules copy, Playwright browsers under
`/opt/pp-shared`). Before turning the runner back on, run one order by hand (`workflow_dispatch`) and read the log.
Off switch, not recommended: repository variable `PP_AGENT_ISOLATION = false`.

**Owner, after merging:** the service key has been reachable by agents since the runner went live. Nothing shows it
was taken, but rotating it is cheap: rotate the Supabase service key (Project Settings → API) and update the
`PP_SUPABASE_SERVICE_KEY` Actions secret; rotate `PP_AUDIT_TOKEN` the same way.

## High

### 2. Pack text could reach Python `eval`

**What.** `checks/math_check.py` read answers with SymPy's `parse_expr`, which evaluates the Python it builds with every
builtin in reach. A math key in an agent-written pack (shaped by the teacher's sources) ran as code on the runner.

**Fix.** Commit `5a39978`: text with dunders, quotes, attribute access or Python keywords is unreadable, and `eval`
sees only a list of SymPy math functions and no builtins. `scripts/security-check.mjs` runs real payloads (and its
self-test shows they do run through plain `parse_expr`).

### 3. Supabase default grants; no limit on orders

**What.** Supabase grants every new table and function in `public` to `authenticated` by default. The first migration
revoked `anon` and `public` but never `authenticated`, so any signed-in teacher could:
- call `orders_due_for_purge()` and get the id, teacher id and status of other teachers' finished orders;
- change her own `teachers.email` (the owner's dashboard shows it);
- send any number of orders, each of which starts the paid automatic runner, with any number and size of fields.

RLS itself held: no teacher can read or change another teacher's orders, events or files, change her own order's
status, price or approval directly, or skip the follow-up (the four functions check her id and the status).

**Fix.** Commit `0527b3f`, a new migration `supabase/migrations/20261109120000_security.sql`: only the grants the site
uses (insert only the six columns the order page sends), size limits, and an insert trigger that keeps every upload
path inside her own order folder and allows at most 10 orders a day and 5 open at once (the owner is not limited).
The fake Supabase models it; `scripts/test-orders.mjs` tries a stolen upload path, a sixth open order and the purge
list as a teacher; `scripts/security-check.mjs` fails on any function never revoked from or granted to
`authenticated`, and on a `security definer` function without `set search_path`.

**SQL the owner must run** (Supabase → SQL Editor, once, after merging): the whole file
`supabase/migrations/20261109120000_security.sql`. It changes no data. The limits (10 a day, 5 open) are a starting
point: change the numbers in a later migration if the pricing plans need others.

### 4. The auditor publishes order-derived records, and can carry a prompt across teachers

**What.** After each final, the auditor's gate commits `records/<order>.json` and an AI-written report in
`docs/audits/` to `main`. The repository is public, and Vercel serves the repository root, so both are on the public
site. The record leaves out her documents, style and requests, but keeps her topic and every finding and log line,
which can quote her questions or sources. The auditor also edits the briefs every later order uses; the gate refuses
weakened rules but not new instructions, so a prompt hidden in one teacher's upload could reach every later
teacher's pack.

**Owner decision** (not changed here: it is the auditor's design and an owner-gated path):
- keep records and audit reports out of the public repository (private storage, or make the repository private and
  stop serving it, finding 8);
- have the auditor read only the scripted findings and counts, never free text that came from her order;
- or send brief changes caused by an order through the `owner-ok` label instead of straight to `main`.

## Medium

### 5. No anti-framing or other security headers

**What.** No `X-Frame-Options` or `frame-ancestors`: another site could frame My orders and trick a signed-in teacher
into pressing Approve or Cancel. **Fix.** Commit `e2bdf07`: `X-Frame-Options: DENY`, `Content-Security-Policy:
frame-ancestors 'none'; object-src 'none'; base-uri 'self'`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` on every
path. `npm run serve` now applies `vercel.json`'s headers, so the order and interactive tests run under them (both
pass, the sandboxed "Try it here" frame included). A full script CSP was left out on purpose: the preview frame is a
`srcdoc` frame, which inherits the page's policy and would block the interactive page's own scripts.

### 6. mathjs advisories

`scripts/versions.mjs` evaluates agent-written formulas with mathjs 13, which has two high advisories (unsafe object
property setters). **Fix.** Commit `15b54be`: mathjs 15.2; `scripts/test-versions.mjs` passes, its refusals included.

### 7. The price comes from the browser

`orders.token_total` is whatever the order page sends, and the runner's automatic-or-bigger rule reads it. No money
changes hands yet, so the harm today is a bigger order on the automatic path (onboarding recomputes the budget, and the
item and size rules still apply). **Owner decision before billing goes live:** compute the price on the server (an
Edge Function or a database function reading the menu prices), or have the runner recompute it from `menu.json` and
hand off any order whose total doesn't match.

### 8. Vercel publishes the whole repository

`vercel.json` has `"outputDirectory": "."`: every tracked file is on the site (`/CLAUDE.md`, `/agents/…`,
`/scripts/…`, `/supabase/…`, `/records/…`, `/docs/audits/…`). The repository is public today, so this adds nothing
new; it matters the day the repository goes private. **Owner decision:** publish only `site/`, `backend.config.json`
and `api/` (a build step that copies them into an output folder).

### 9. The model API key in every agent session

Claude Code needs it, so every session has it, and an injected prompt could misuse it (cost only: it reaches no
teacher's data). **Owner decision:** give the runner its own key in its own workspace with a monthly spend limit.

## Low

10. **Orphan uploads.** Files uploaded for an order that was never sent (a closed tab mid-upload; the page tries to
    delete them, but can't always) have no order row, so `orders_due_for_purge` never finds them. Next run: have
    `orders.mjs purge --due` also delete upload folders with no order after a day.
11. **localhost in the redirect list.** `docs/BACKEND.md` step 5 adds `http://localhost:4321/site/**` to the
    production project's Redirect URLs. Keep it only in a test project.
12. **Chromium `--no-sandbox`.** The renderer and the checks open AI-written pages (with their scripts) in Chromium
    without its sandbox on the runner. Exploiting it needs a browser bug; worth dropping the flag where the runner
    allows the sandbox.
13. **Claude Code at `latest`.** Set the `PP_CLAUDE_CODE_VERSION` variable to a tested version.
14. **npm audit, what's left.** katex (low, needs prototype pollution elsewhere first) and image-size through pptxgenjs
    (a slow loop on crafted images; the images are ones we render). No fix without a major downgrade; recheck monthly.
15. **Cancel during a build.** The runner sets the next status without checking for `cancelled`. Not a security hole;
    the order would come back to life. Next run.

## Checked and fine

- RLS on `teachers`, `admins`, `orders`, `order_events`: own rows or the owner; no teacher update or delete on orders.
- `answer_follow_up`, `request_changes`, `approve_order`, `cancel_order`: `security definer` with `set search_path`,
  her id and the status checked; the approval is bound to the preview's pack hash, agreement text and every PDF hash.
- Storage: `uploads` and `deliverables` are private; reads, uploads and deletes are limited to her own top folder;
  signed URLs last 10 minutes (page viewer) and are made per file.
- The page viewer (`site/page.js`): `p` must be `<uuid>/<order>/(preview|final)/<file>.html`, storage still checks the
  folder, and the page runs in a sandbox without `allow-same-origin`, so it can't reach the site, its storage or its
  session. Interactive pages must carry a CSP that forbids every request (`checks/interactive-format.mjs`).
- Teacher text on My orders, the review page and the owner's dashboard is escaped everywhere it is inserted.
- Workflows: no `${{ }}` inside `run:` scripts (now a check), the order id is validated before use, checkouts keep no
  token, CI on pull requests has no secrets, and the owner gate covers `.github/`, `supabase/` and `site/backend.js`.
- No secret in the repository or its history; the public `backend.config.json` holds a publishable key, and
  `scripts/build-backend-config.mjs` refuses a service key.
- `api/fetch-page.js`: signed-in only, rate-limited, and a careful SSRF guard (public addresses only, pinned DNS,
  redirects rechecked, size and time limits).
- Emails (`scripts/notify-order.mjs`): plain text, no requests or files, header injection tested.
